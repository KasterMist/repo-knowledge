# Repo Knowledge：任务、进度与续接入口

更新日期：2026-10-23。所有者：KasterMist。仓库：[KasterMist/repo-knowledge](https://github.com/KasterMist/repo-knowledge)。许可证：Apache-2.0。

本表依据对话中确认的需求、仓库实现与验收记录，以及当日核对的 GitHub Issue #1/#3/#5 整理。核对起点为已合并的 90b2dcb（PR #8）。实现完成、自动化测试通过、人工验收通过和正式发布是不同状态，不相互替代。本表不按聊天轮数或代码量估算完成百分比。

## 1. 已确认需求，后续不得遗忘

1. 做一个开源 VS Code 插件，提供接近 Qoder Repo Wiki 的知识阅读和 Agent 知识使用体验；不承诺复刻其私有内部机制。
2. 面向用户的 Wiki 与面向 Agent 的知识卡片共享规范知识来源，保留修订、代码证据、源码版本及人工设计理由。
3. **是否生成由用户决定。** 扫描、首次生成、重新生成和增量更新由用户主动发起，并选择范围。打开仓库、保存代码或切换分支不得静默触发模型调用、生成、重写或发布。
4. 生成形成可审阅候选，经用户审阅确认后发布；不能悄悄覆盖人工知识。过期状态检查与生成分开。
5. 优先集成官方 Codex VS Code 扩展；通过独立 MCP 和编辑器无关内核为其他 Agent 保留接入能力。其他 Agent 尚未真实验收；模型生成适配器与 MCP 检索接入是两回事。
6. Windows 与 Linux 必须支持；**Windows VS Code Remote SSH → Linux 是必需且重要的使用场景**。Remote SSH 通过不等于原生 Linux 桌面验收通过。
7. “学习”是保存和跨会话重新读取项目知识，不是训练模型，也不保证 Agent 每轮必然主动调用工具。
8. 不要求管理员权限完成远端 MCP 使用；现有 VS Code Server Node 已用于真实远端验证。敏感连接信息、用户配置、私有源码不得进入 GitHub 或公开验收材料。

## 2. 当前产品边界

已实现：知识 schema、三卡片演示、源码证据/过期检查、词法检索、四个独立 STDIO MCP 工具、不可变候选，以及六个 VS Code 命令。模块为 packages/core、packages/mcp-server、packages/vscode-extension。

当前是 **M1 实现预览**。已有真实候选 VSIX，但没有版本化 alpha Release、Marketplace 版本、完整 Wiki 树/编辑工作台、审阅发布界面、用户发起生成或完整增量维护。现有卡片是自编 fixture，不能据此声称任意仓库知识生成已完成。

## 6. 每次开发与 GitHub 交付流程

1. 读取本文件、requirements、对应 roadmap 任务及 ADR；核对工作区和远端实际状态。明确本次小工作包及验收条件。
2. 在关联 Issue 中记录场景、依赖、范围、验证和退出条件。小 PR 推进，避免把整个里程碑堆成一次变更。
3. 在工作分支实现。core 保持编辑器无关；MCP 独立进程；VS Code 负责界面与接入。持久格式变化需 ADR、迁移和回退方案。
4. 实现变更运行锁定工具链与 npm run check；按风险做边界/进程/实际 VSIX 验证。文档变更检查格式、链接和仓库策略。只执行自编 fixture，不执行目标项目源码、测试、构建或基准。
5. 检查精确提交清单，排除凭据、用户配置、私有路径、源码及忽略的本地 helper。用户无需发送 token 或公开服务器信息。
6. 用已授权 GitHub 连接器或正常 Git 提交 PR；描述问题、结果、证据、兼容影响和未覆盖项。核对确切 head 的 Windows/Linux 与远端运行时 CI。
7. 检查通过后按任务授权合并；同步本地主分支，保留必要工作。更新 Issue 正文、证据和本表，避免“评论已通过而正文仍说未测试”。
8. 只有退出条件齐全才关闭任务；实现完成、待验收、待发布必须分开。每次交接给出“本次改变、依据、未完成、下一步”。

## 7. alpha 与后续版本发布流程

1. 先完成相应平台/真实 Agent/实际 VSIX 门禁，固定发布源提交和支持矩阵。
2. 统一产品版本、tag、changelog、知识格式版本和升级/回退说明；不得把当前 0.0.0 测试候选直接描述为已发布 alpha。
3. 从已检查提交构建一次，验证 VSIX 内容和独立 MCP，生成 SHA-256。
4. 创建 draft prerelease，上传实际 VSIX、SHA256SUMS 和准确的限制/安装说明；检查资产后发布。
5. 下载公开资产，重新核对校验和与安装路径，记录结果，再关闭 T10。已发布 tag/资产不原地替换，修复另发版本。
6. Marketplace 单独处理 Publisher/认证；不需要管理员权限或用户把凭据贴到对话中。

详细规则见[发布流程](releasing.md)。当前无 alpha Release、无 Marketplace 发布。

## 8. 后续会话如何恢复工作

从本文件第 5 节的第一个未完成门禁继续，先读证据，避免重测已通过的核心 Remote SSH 场景。若状态变化，更新本表、相关验收文件及 Issue 正文；新增需求先更新 requirements/roadmap，再实现。若与新用户指令冲突，以较新的明确用户指令为准并修正文档。

远端连接资料和本地交接 helper 保留在公开仓库之外；不能为了“防遗忘”将它们写进本表。未来会话缺少可用环境时，先说明缺口，不猜测凭据、配置或完成状态。
