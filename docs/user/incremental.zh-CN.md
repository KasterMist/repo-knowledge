# 用户发起单卡增量更新（T20 开发版）

本功能尚未发布，也不会在保存代码或切换分支时自动调用模型。
Generate Knowledge Candidate 仍用于新增卡片；更新已有卡片使用下面的命令。
请使用当前工作树/分支已绑定的外部知识目录，先完整备份。

1. 运行 **Review Knowledge Changes** 查看相对于已保存依赖基线的影响。
   报告只读，不调用模型。检查哪些卡片的直接证据失效，哪些只是潜在影响。
2. 运行 **Plan Knowledge Generation**，选择本次更新所需的当前源码范围。
   修改源码后必须使用新规划，不能复用旧指纹。
3. 运行 **Generate Card Update**，选择一张已有卡片。确认框列出源码路径，
   并说明将发送所选已保存源码和该卡片全文给当前配置的模型/提供方。
   取消不建立尝试、不启动模型。确认后最多提交一个生成任务，限时 60 秒，
   只接受一个同 ID 的卡片结果；这不是精确费用上限。
4. 成功后只保存新候选，不发布。打开的 incremental-result.json 含尝试 ID、
   proposalId、耗时、请求尝试次数及可用的观察 token 数。未知 token 数为 null；
   请求尝试次数不是账单调用数。候选位于 **Proposals**，不是 New Cards。
5. 运行 **Review Proposal Diff**，核对旧事实是否更新、人工设计理由是否保留、
   证据是否对应当前源码。满意后 **Publish Reviewed Proposal** 并单独确认。
   不满意就保留未发布候选；修改代码或知识后不能绕过修订/证据检查。

一轮发布或回退完成后，旧依赖基线的知识快照可能已失效。继续下一轮前，显式
重新规划并 Capture Dependency Baseline；旧基线保留作记录，不覆盖或伪造其指纹。

**Recover Incremental Result** 只读已保留尝试并找回候选/状态，不会启动模型或
重复发布。失败、取消或崩溃后先用它检查。no-result 表示没有可用候选，不代表
模型一定没有产生用量；needs-merge/needs-source-refresh 表示应重新审阅或更新。
若需要重试，重新规划并显式运行 Generate Card Update，再确认一次新请求。
不要反复重试网络错误，也无需据此修改登录、模型或提供方。

如果知识在候选保存后有人工更新，可用 [T19 三方合并](three-way-merge.zh-CN.md)。
生成期间源码或知识变化则结果被拒绝，不会自动覆盖人工版本。

回退仍使用 History 和 **Roll Back Knowledge**：先检查差异，再次运行并确认。
旧版本的证据不再匹配当前源码时会拒绝回退。应先明确恢复相应源码版本，再
回退知识；不要通过改哈希伪造有效证据。beta 自编演示会单独保存/恢复原始源码，
不操作你的其他项目。

首次 beta 覆盖有界单卡更新；不是全库多轮生成。无交集的删除/改名范围需要
人工检查适用范围。格式、迁移和失败恢复见 [ADR 0013](../architecture/adr/0013-incremental-attempts.md)。
