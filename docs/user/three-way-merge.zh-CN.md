# 合并旧建议与当前人工知识（T19 开发版）

此功能尚未发布。它不会调用模型或直接发布，只创建新的合并草稿。

当建议生成后你又修改了同一张卡片，旧建议直接发布仍会被修订冲突拒绝。
对于带有原始卡片的新候选，可用下面的方式保留人工修改并审阅旧建议。

1. 运行 **Repo Knowledge: Merge Proposal into Draft**，选择旧候选。
   第一次打开只读 JSON：`base` 是建议产生时的卡片，`current` 是当前卡片，
   `proposed` 是旧建议，`merged` 是保守合并结果，`conflicts` 是冲突字段。
2. 检查三份内容，再运行同一命令并选择同一候选。确认“创建草稿 / Create draft”。
   取消不创建草稿，也不改变知识。若上下文变了，会先要求重新查看报告。
3. 在打开的草稿中编辑 `proposedCard`。不同字段的修改已合并；冲突字段默认
   保留当前人工内容。正文双方都改过时，整段正文视为冲突，不会猜测语义。
4. 处理并检查所有冲突后，填写 `merge.resolvedFields`。例如报告为
   `conflicts: ["body"]`，则填写 `resolvedFields: ["body"]`。选择保留当前正文
   也需要这样确认；没有冲突时保留空数组。不要改 baseCard、基础修订/快照、
   reviewId 或不可变合并记录。未确认冲突会拒绝提交。
5. 保存草稿，运行 **Submit Draft for Review**，选择新草稿，形成新候选。
   再查看新候选差异，运行 **Publish Reviewed Proposal** 并单独确认发布。
   原建议仍保留；回退仍走历史差异和确认流程。

如果处理期间人工知识、源码证据、分支、HEAD 或暂存区再次变化，提交可能被
拒绝。保留旧草稿，重新读取并从新的三方报告开始，不要改修订号绕过检查。

旧格式候选没有记录原始卡片，会提示 `MERGE_BASE_UNAVAILABLE`。请保留旧建议，
从当前卡片创建新人工草稿并逐项比较；插件不会把当前内容冒充历史原文。

三方报告和草稿只保存在本宿主外部知识目录；Remote SSH 使用服务器上的目录。
升级/回退及格式细节见 [ADR 0012](../architecture/adr/0012-three-way-merge.md)。
